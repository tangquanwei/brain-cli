# 白板实现计划：从当前原型走向 Heptabase

> 目标产品：以 Heptabase 的“卡片 + 空间化组织 + 知识来源”体验为参考，保持 2ndBrain 的本地优先、Markdown 可移植和 Git 可追踪特性。
>
> 说明：文档中的“白板”指当前 WebUI 的 Whiteboard 页面；“Heptabase”是目标体验参考（用户请求中的 `hetabase` 统一按 Heptabase 记录）。

## 1. 产品目标

白板不是独立的笔记编辑器，而是知识库的空间化视图：

1. 用户可以把 Markdown 笔记、摘录和临时想法放到同一张无限画布上。
2. 用户可以通过位置、颜色、分组和连接表达关系，而不必改变原始 Markdown 文件。
3. 白板上的卡片可以回到事实来源，笔记内容变化后不会产生两个互相冲突的真相源。
4. 所有数据默认保存在本地知识库中，格式可读、可备份、可迁移。

### 当前产品边界

- 知识库事实来源仍是 `notes/**/*.md`。
- 白板只保存空间状态、卡片覆盖内容和连接关系，位于 `notes/.brain/whiteboards/`。
- 第一阶段不做实时多人协作、云端账号和服务端数据库。

| 能力 | 当前状态 | 主要限制 |
| --- | --- | --- |
| 白板数量 | 部分实现 | API 有 `id`，但 UI 固定使用 `research-map`，没有白板列表、复制、归档和删除。 |
| 卡片导入 | 部分实现 | 只导入笔记摘要；没有高亮、附件、网页剪藏、PDF 页面或块级引用。 |

| 数据同步 | 部分实现 | 保存到本地 JSON；没有冲突检测、版本历史、撤销/重做和跨设备同步。 |
| 画布组织 | 未实现 | 没有框选、多选、分组、区域标题、自动布局、对齐、吸附和层级。 |

| 移动端 | 部分实现 | 基础拖拽可用，但没有专门的触控手势、底部工具栏和窄屏卡片编辑体验。 |
| 协作 | 未实现 | 没有多人、评论、权限、分享链接和实时协作。 |

以下规范参考 draw.io 的画布交互，但会保留 2ndBrain 的卡片语义和本地优先行为。手势必须在不选中卡片、选中卡片、连接模式三种状态下有明确且一致的结果。

| --- | --- | --- |

| `Space` + 拖动 | 临时平移画布，适合从卡片上开始拖动画布 | 待实现 |
| 鼠标中键拖动 | 平移画布 | 待实现 |
| 滚轮 | 垂直滚动画布；画布无页面滚动时转换为平移 | 待实现 |
| `Ctrl/Cmd` + 滚轮 | 以鼠标位置为中心缩放 | 部分实现（已有按钮缩放，尚未绑定滚轮和焦点） |
| 点击卡片 | 选中卡片并打开属性面板 | 已实现 |
| `Shift` + 点击卡片 | 增加/移除多选项，不清除已有选择 | 待实现 |

| `Delete` / `Backspace` | 删除选中的卡片、连接或 frame；删除前提供可撤销反馈 | 部分实现（卡片删除按钮） |

| 连接端点拖动 | 从卡片连接柄拖到目标卡片；悬停目标时显示可连接反馈 | 部分实现（按钮进入连接模式后点击目标） |

| 右键卡片或空白处 | 打开上下文菜单：编辑、复制、删除、连接、置顶、适配视图 | 待实现 |
| `Ctrl/Cmd` + `A` | 选中当前白板全部可见卡片 | 待实现 |
| `Ctrl/Cmd` + `0` | 适配全部内容；`Ctrl/Cmd` + `1` 回到 100% | 待实现 |

### 4.2 工具状态和反馈

- [ ] 工具栏增加“选择 / 平移 / 连接”三态工具，当前工具有明显 active 状态。
- [ ] 连接模式下，来源卡片、可连接目标和不可连接目标使用不同的 hover/outline 样式。

- [ ] 拖动卡片时显示对齐辅助线；接近网格或其他卡片时吸附，但允许按 `Alt/Option` 临时关闭吸附。

| 手势 | 目标交互 | 当前状态 |
| --- | --- | --- |
| 单指拖动空白处 | 平移画布 | 部分实现 |
| 单指拖动卡片 | 移动卡片 | 已实现 |
| 双指捏合 | 以两指中心缩放 | 待实现 |
| 双指拖动 | 平移画布，不移动卡片 | 待实现 |
| 单击卡片 | 选中并打开底部/侧边编辑面板 | 部分实现 |
| 长按卡片 | 打开上下文操作菜单 | 待实现 |
| 双击/双指轻点 | 编辑卡片标题或正文 | 待实现 |
| 双指点击或返回手势 | 退出连接/编辑/选择状态 | 待实现 |

移动端不强行复刻桌面右键和键盘快捷键：这些能力应由长按菜单、底部工具栏和清晰的撤销按钮替代。触控命中区域建议不小于 44px，卡片拖动过程中要避免页面跟随滚动。

### 4.4 交互优先级和验收顺序

1. **P0：不误操作**：`Esc` 取消状态、删除可撤销、连接目标有反馈、拖动画布与拖动卡片不冲突。
2. **P1：高频效率**：框选、多选、复制/粘贴、方向键移动、撤销/重做、滚轮缩放。
3. **P2：组织效率**：吸附、对齐、正交连接、frame 批量移动、右键菜单。
4. **P3：触控体验**：捏合缩放、双指平移、长按菜单、移动端底部工具栏。

验收时至少覆盖以下流程：

```text
打开白板 → Space+拖动平移 → Ctrl/Cmd+滚轮缩放 → 框选两张卡片
→ Shift+点击追加卡片 → Alt/Option+拖动复制 → 连接柄拖到目标
→ Delete 删除 → Ctrl/Cmd+Z 恢复 → Ctrl/Cmd+0 适配全部内容
```

## 5. AFFiNE 白板实现参考

本节基于 AFFiNE 当前开源仓库的 BlockSuite/Edgeless 实现整理。源码仓库：<https://github.com/toeverything/affine>。

### 5.1 文档模型：页面和白板共用一份文档

AFFiNE 的 edgeless 模式不是另一种文件格式。一个文档的根节点同时包含：

```text
Root Block
├── Surface Block          # 画布图形层
│   ├── Shape / Brush / Connector 等 SurfaceElement
│   └── 可放置在画布上的 Embed/Frame 等 Block
├── Note Block              # 可在页面模式和白板模式复用
└── Note Block ...
```

- Surface Block 的 `elements` 使用 `Y.Map` 保存图形元素。
- Note、图片、嵌入文档等仍是 Block，可同时出现在页面流和白板空间。
- 可排序对象都有 `index` 和 `xywh`；`index` 使用 fractional indexing 维护层级，`xywh` 统一表示绝对坐标与尺寸。
- 这让“同一篇笔记既能在页面阅读，也能作为白板卡片摆放”成为模型能力，而不是导入时复制一份内容。

对应源码位置（上游仓库）：

- `blocksuite/docs-site/components/editors/edgeless-data-structure.md`
- `blocksuite/affine/blocks/surface/src/surface-model.ts`
- `blocksuite/affine/blocks/surface/src/surface-block.ts`
- `blocksuite/affine/blocks/root/src/edgeless/edgeless-root-service.ts`

**对 2ndBrain 的取舍**：我们继续使用可读 JSON，不引入 Yjs 作为本地存储依赖；但应借鉴“笔记对象与画布元素分离”的结构，把当前 `sourceId` 升级为稳定的 `source` 引用，把卡片和 frame 作为统一的 indexable 元素。

### 5.2 渲染：画布层和可编辑 DOM 分离

AFFiNE 的 Surface Block 有两套渲染器：

- `CanvasRenderer`：适合大量 shape、brush、connector 等高频绘制内容。
- `DomRenderer`：适合需要原生输入、选区和可访问性的可编辑 Block。
- 渲染器通过 element type 注册扩展，新增元素不需要修改中心渲染循环。
- 视口、缩放和元素坐标统一转换，渲染器只处理“模型坐标 → 屏幕坐标”。

对应源码位置：

- `blocksuite/affine/blocks/surface/src/renderer/canvas-renderer.ts`
- `blocksuite/affine/blocks/surface/src/renderer/dom-renderer.ts`
- `blocksuite/affine/blocks/surface/src/extensions/element-renderer.ts`

**对 2ndBrain 的取舍**：当前“DOM 卡片 + SVG edge”适合 MVP，可以保留；当卡片和连接数量增长后，将 edge、选区框、辅助线和背景网格放入单独 Canvas/SVG 层，卡片继续使用 DOM，以兼顾性能和编辑体验。

### 5.3 交互：工具、viewport、selection 是独立服务

AFFiNE 把输入处理拆成可组合的工具和服务，而不是让每个卡片组件自己判断所有 pointer 事件：

- `GfxController` 统一管理 viewport、layer、selection 和当前 tool。
- `EdgelessRootBlockComponent` 处理 pan、pinch、wheel，并支持以鼠标位置为中心缩放。
- `DefaultTool`、`PanTool`、`ConnectorTool`、`ShapeTool` 等工具拥有独立的 pointer 生命周期。
- 按住 `Space` 临时切换到 pan，松开后恢复原工具；工具切换不会破坏正在编辑的文本。
- 选择状态集中在 `SurfaceSelection`，框选、多选、远程选择和选中框由 selection 层统一绘制。
- 拖动到视口边缘时会自动平移，避免用户无法选择画布外的对象。

对应源码位置：

- `blocksuite/affine/blocks/root/src/edgeless/edgeless-root-block.ts`
- `blocksuite/affine/blocks/root/src/edgeless/edgeless-root-service.ts`
- `blocksuite/affine/gfx/pointer/src/tools/pan-tool.ts`
- `blocksuite/affine/gfx/pointer/src/tools/default-tool.ts`
- `blocksuite/affine/gfx/connector/src/connector-tool.ts`
- `blocksuite/affine/widgets/edgeless-selected-rect/src/`

**对 2ndBrain 的落地顺序**：先抽出 `useWhiteboardViewport`、`useWhiteboardSelection` 和 `useWhiteboardTool` 三个状态边界，再把 React 组件变成渲染层。这样可以避免继续在 `Whiteboard.tsx` 中累积所有手势分支。

### 5.4 Connector：端点引用、路径算法和标签分开

AFFiNE 的 connector 不只保存一条从 A 到 B 的线：

- `source` 和 `target` 可以引用元素 id，也可以保存相对端点位置。
- 支持直线、正交折线和曲线三种 mode。
- 连接线有独立的 stroke、端点样式、宽度、虚线和 roughness。
- 标签是 connector 的独立文本属性，拥有自己的位置、宽度和编辑状态。
- Surface Block 建立“元素 id → 连接线”的索引，元素移动、删除或重连时可以快速更新关联 connector。
- 删除可连接元素时，关联 connector 会随之删除，避免孤立 edge。

对应源码位置：

- `blocksuite/affine/model/src/elements/connector/connector.ts`
- `blocksuite/affine/gfx/connector/src/connector-manager.ts`
- `blocksuite/affine/blocks/surface/src/commands/reassociate-connectors.ts`
- `blocksuite/affine/blocks/surface/src/extensions/crud-extension.ts`

**对 2ndBrain 的落地顺序**：先把现有 `{ from, to }` 扩展为 `source/target` + `kind` + 可选 `label`，再实现正交路径和连接柄；不要在 UI 层硬编码 edge id 的显示逻辑。

### 5.5 Frame 和 Group 是两种不同关系

AFFiNE 明确区分：

- **Frame**：有自己的 `xywh` 区域，卡片位于区域内就形成空间关联；移动 frame 可以带动区域内元素，frame 可以重叠但不嵌套在 block tree 中。
- **Group**：没有独立空间尺寸，只记录 child ids；移动/变换 group 会作用于明确的子元素，并且允许嵌套。

这比单纯给卡片增加 `groupId` 更稳定：frame 表达“区域归属”，group 表达“操作绑定”。对应源码位置：

- `blocksuite/affine/model/src/blocks/frame/frame-model.ts`
- `blocksuite/affine/model/src/elements/group/group.ts`
- `blocksuite/affine/gfx/group/src/command/group-api.ts`

**对 2ndBrain 的落地建议**：先实现 Frame（研究阶段、问题、证据、结论），暂不实现任意嵌套 Group；等多选和批量变换稳定后再加入 Group。

### 5.6 历史记录、协作和测试

- AFFiNE 使用 BlockSuite Store 的 `Y.UndoManager`，以文档 transaction 为单位记录撤销/重做。
- 同一份 Yjs 文档可以接入实时同步和远程 selection，但这依赖完整的协作协议、身份和冲突处理。
- Edgeless 有大量按交互流程组织的 E2E 测试，覆盖 pan、pinch、框选、resize、rotation、connector、frame、group、clipboard、shortcut 和移动端行为。

对应源码位置：

- `blocksuite/framework/store/src/extension/history/history-extension.ts`
- `tests/blocksuite/e2e/edgeless/`

**对 2ndBrain 的取舍**：本地版本先用命令快照栈实现 undo/redo，并为每个操作写 E2E 测试；只有确定需要多人实时编辑时，才评估 Yjs/协作服务，而不是为了“像 AFFiNE”提前引入。

### 5.7 AFFiNE 参考结论

AFFiNE 最值得借鉴的是边界设计：

```text
文档模型（Block/SurfaceElement）
        ↓
统一状态（Viewport/Layer/Selection/Tool/History）
        ↓
渲染器（Canvas + DOM + Overlay）
        ↓
交互工具（Pan/Select/Connect/Shape/Text）
```

我们当前的最小对应关系是：

| AFFiNE 概念 | 2ndBrain 当前实现 | 下一步 |
| --- | --- | --- |
| Surface Block | `WhiteboardDocument` | 拆出 `elements`/`frames`，保留 JSON |
| SurfaceElement | `WhiteboardCard` / `WhiteboardEdge` | 增加 `kind`、`xywh`、`index`、标签 |
| Gfx viewport | `viewport: { x, y, zoom }` | 统一鼠标中心缩放、手势和 fit |
| SurfaceSelection | `selectedId` | 多选、框选、选择层 |
| Edgeless tools | 连接按钮 + pointer handlers | 选择/平移/连接工具状态机 |
| Canvas + DOM renderer | SVG edge + DOM card | 大数据量时分层渲染 |
| Frame / Group | 尚未实现 | 先 Frame，后 Group |
| Y.UndoManager | 尚未实现 | 本地命令栈，协作时再评估 Yjs |

## 6. Heptabase 目标能力拆解

我们不复制 Heptabase 的全部产品，而是优先实现对本地知识库最有价值的部分：

### P0：稳定的数据基础

- 白板 schema 升级到 `version: 2`，保留 v1 读取和迁移。
- 把 `card`、`group/frame`、`edge`、`viewport` 分成稳定的数据类型。
- 为每个对象增加 `createdAt`、`updatedAt` 和可选 `zIndex`。
- 所有写操作采用版本号或更新时间检查，避免多个页面互相覆盖。
- 为白板读写、迁移和外部变更补齐测试。

**验收标准**：旧版 `research-map.json` 可无损打开；非法或过大的数据被拒绝；写入中断后原文件仍可读取。

### P1：多白板和基础编辑能力

- 新增白板列表页或白板选择器：创建、重命名、复制、删除、归档。
- 从固定 `research-map` 改为路由参数 `/whiteboard/:id`。
- 支持多选、框选、批量移动、批量改色和批量删除。
- 增加撤销/重做（先在前端维护操作栈，保存时写入最终状态）。
- 支持 draw.io 风格键盘和鼠标操作：删除、复制、撤销/重做、滚轮缩放、适配画布、方向键移动。
- 增加选择/平移/连接工具状态，以及右键菜单和明确的取消反馈。

**验收标准**：用户可以创建两张互不影响的白板；刷新、切换路由后每张白板状态都能恢复。

### P2：知识卡片能力

- 笔记卡片：显示标题、摘要、标签、来源路径和最后更新时间。
- 文本卡片：适合临时想法，不强制创建 Markdown 文件。
- 块引用卡片：引用某篇笔记的标题或段落，并能跳回来源位置。
- 图片/附件卡片：引用 notes 内的图片、PDF 或其他附件，不复制文件。
- 卡片支持标签、颜色、状态和自定义图标；纯文本字段继续保持可迁移。
- 编辑卡片时提供 Markdown 编辑/预览，避免正文只能作为一行摘要。

**验收标准**：来源笔记、临时文本和附件都能放在同一画布；点击来源能打开对应文件；移动文件后 sourceId 不会静默失效。

### P3：空间组织和视觉语义

- Frame/Group：用带标题的区域组织卡片，例如“问题”“证据”“结论”“下一步”。
- 支持将卡片拖入/移出 frame，frame 移动时可选择是否带动子卡片。
- 支持对齐、等间距、网格吸附和简单自动布局。
- 连接支持标签、颜色、关系类型（支持、反驳、因果、引用等）。
- 增加颜色/标签/来源类型筛选，并提供“只显示当前选择的邻居”。

**验收标准**：一张研究白板可以清晰表达至少三个区域和两种关系；筛选不会破坏原始坐标和连接。

### P4：导航和知识库联动

- 小地图（minimap）和“适配全部内容”。
- 从笔记页、图谱页直接把选中笔记加入当前白板。
- 白板卡片显示反向链接数量、标签和关联笔记。
- 白板外部 JSON 变化通过 SSE 触发当前白板重新加载，并提示“本地内容已更新”。
- 当笔记重命名或移动时，使用稳定 note id/相对路径迁移 sourceId。
- 提供“从白板生成笔记关系报告”的只读导出，不直接改写 Markdown。

**验收标准**：用户可以从笔记、图谱、白板三处来回跳转；外部修改在不刷新浏览器的情况下可见；来源文件不存在时有明确断链提示。

### P5：本地协作和可选同步

这一阶段必须在本地优先稳定后再考虑：

- Git 历史中的白板版本浏览和恢复。
- 同一 notes 仓库多设备同步时的冲突提示和三方合并辅助。
- 可选的只读分享导出（静态 JSON/HTML/图片），不默认上传内容。
- 多人实时协作、账号和权限属于独立产品范围，暂不纳入核心版本。

**验收标准**：同步失败不会覆盖本地状态；冲突可解释、可恢复；导出不泄漏工作区之外的文件。

## 7. 建议的数据模型（v2 草案）

```json
{
  "version": 2,
  "id": "research-map",
  "title": "研究地图",
  "cards": [
    {
      "id": "card-1",
      "kind": "note",
      "source": { "noteId": "resources/example.md" },
      "title": "可迁移的 Markdown",
      "body": "标准 Markdown 让知识库保持可读。",
      "tags": ["local-first"],
      "color": "blue",
      "x": 120,
      "y": 90,
      "zIndex": 1,
      "createdAt": "2026-08-27T00:00:00.000Z",
      "updatedAt": "2026-08-27T00:00:00.000Z"
    }
  ],
  "frames": [],
  "edges": [
    {
      "id": "edge-1",
      "from": "card-1",
      "to": "card-2",
      "label": "supports",
      "kind": "semantic"
    }
  ],
  "viewport": { "x": 24, "y": 24, "zoom": 1 },
  "updatedAt": "2026-08-27T00:00:00.000Z"
}
```

### 迁移原则

1. v1 的 `sourceId` 映射为 `source.noteId`，没有来源的卡片映射为 `kind: "text"`。
2. v1 的 `color`、坐标、正文和 edge 原样保留。
3. 新字段全部可选，读取时提供默认值；写回时再升级为 v2。
4. 不把笔记正文复制成白板的唯一来源；卡片正文只作为快照或覆盖内容。

## 9. 非目标和决策约束

- 不在白板中复制一套完整 Markdown 编辑器；复杂编辑回到笔记页或 VS Code。
- 不引入云端数据库作为白板的唯一存储。
- 不为了视觉效果牺牲键盘可用性、移动文件后的来源稳定性和 Git 可审计性。
- 不在没有性能基准前引入重量级画布引擎；当卡片数量或交互复杂度超过 DOM/SVG 的舒适范围时，再评估 Canvas/WebGL。
- 每一个新白板能力都需要同时考虑：JSON 兼容、路径安全、外部修改、撤销/恢复和测试。

## 10. 当前结论

当前实现已经是“可用的单白板知识地图原型”，核心的卡片、拖拽、缩放、导入、连接和本地持久化已经具备。距离 Heptabase 风格的完整体验，最重要的缺口不是再增加装饰，而是按 **多白板 → 多选/撤销 → 丰富卡片 → Frame/标签/关系 → 来源同步** 的顺序补齐结构化能力。

第一优先级建议锁定为 P0 + P1：先让数据模型和编辑行为稳定，再扩展卡片类型和视觉组织。这样可以避免在单一 `research-map` JSON 上继续堆叠功能，后续迁移成本最低。
